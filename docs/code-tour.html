Stop 10

Linux networking deep dive

Outcome

Map Cadestro’s layers to effective kernel state and declarative backend configuration without treating them as one thing.

Read in order

  • sdk/sys/netconfig/netconfig.go — addressing/routes
  • sdk/sys/dns/dns.go — resolver policy
  • sdk/sys/network/network.go — Wi-Fi profiles
  • sdk/sys/firewall/firewall.go — packet filtering
  • Traefik HTTPS routes
  • Traefik TCP passthrough

DNS names → resolver; addresses/routes → kernel + NetworkManager/networkd; Wi-Fi → profile; filtering → nftables/firewalld/UFW

Public :8081 carries the Control API, health, SCIM, and terminal HTTP; the web is a separate container routed by Traefik. Public TLS is terminated then re-originated to control. Agent :8082 is raw TLS passed through Traefik, with PROXY v2 before TLS; SNI and the client certificate remain meaningful. The device initiates outbound traffic through NAT and needs no inbound listener. Diagnose device kernel state, not server kernel state; declarative backend profiles can differ until reconciliation.

Exercise: For a failed agent connection, inspect DNS, route, Wi-Fi profile, NAT, firewall, listener, SNI, and certificate in that order; record the source file that owns each layer.

Knowledge check

Does a saved NetworkManager profile prove the packet path? No. Verify effective addresses/routes, resolver state, filtering, and NAT separately; declarative configuration is intent, kernel state is behavior.
